# 결제·주문 대사 절차

교동마을 산지직송 · 내부 업무 문서 · 업무 기준 / 기준일 2037-06-30
(화면 경로: 문서 보기 / 결제·주문 대사 절차)

## 1. 대사 키

네 가지 대사 키를 모두 대조한다. 일부 항목의 일치만으로 동일 결제로 확정하지 않는다.

| 키 | 허용 오차 | 확인 출처 | 없으면 |
|---|---|---|---|
| 승인번호 | 정확 일치 | 결제 승인 내역 | 대사 불가 → §3 M-03 |
| 결제금액 | 정확 일치 (실결제액 기준) | 결제 승인 내역 ↔ 주문 | §3 M-04 |
| 승인시각 | ±5분 | 결제 승인 내역 ↔ 주문 생성 시각 | §3 M-05 |
| 카드 뒷 4자리 | 정확 일치 | 결제 승인 내역 ↔ 고객 제시분 | §3 M-06 |

결제 승인과 주문 레코드 생성 사이의 정상적인 지연을 고려하여 승인시각의 허용 오차를 ±5분으로 적용한다. 초 단위 일치를 요구하거나 허용 오차를 임의로 확대하지 않는다.

**결제금액은 실결제액이다** — 정가·할인 전 금액이 아니라 카드·포인트·쿠폰 분할 구성의 합, 곧 **실제로 받은 금액**이다. 분할결제 건은 **카드분만 따로 대사**하지 않는다.

## 2. 절차

| 순 | 무엇 | 도구 |
|---|---|---|
| ⑴ | **결제 승인 내역 조회** — 승인번호·금액·승인시각·카드 뒷 4자리를 확보 | 시스템 조회 |
| ⑵ | **주문 대조** — 같은 고객·같은 시각대의 주문 레코드를 §1 네 키로 맞춘다 | 시스템 조회 |
| ⑶ | **판정** — §3 표에서 유형을 고른다 | — |
| ⑷ | **처리** — 주문 복구 / 미배송분 환불 / 결제사 조회 접수 중 하나 | §4 |
| ⑸ | **안내** — 어느 유형이었는지 · 무엇을 처리했는지 · **반영에 걸리는 기간**을 함께 말한다 | §6 |

⑴ 결제 승인 내역 조회와 ⑵ 주문 대조를 모두 수행한다. 어느 한쪽의 조회를 누락한 상태에서 환불 불가 또는 중복 결제로 판정하지 않는다.

**조회 없이 "주문 없음"으로 종결하지 않는다.** 고객이 받은 결제 문자는 결제가 일어났다는 신호이고, 주문 조회의 "해당 주문 없음"은 조회가 성공했다는 뜻일 뿐 **결제 사실을 부정하는 값이 아니다.**

## 3. 불일치 유형별 처리

| 코드 | 유형 | 판정 | 처리 |
|---|---|---|---|
| M-01 | 네 키 전부 일치 · **주문 레코드 없음 또는 생성 실패 상태** | **주문 유실** | §4 복구 우선 |
| M-02 | 네 키 전부 일치 · 주문이 **취소 상태** | 취소 처리와 환불 이력 확인 | 환불 미완이면 환불, 완료면 입금 경로 안내 |
| M-03 | 승인번호 **없음** (결제 승인 자체가 없음) | 결제 미완료 또는 **타사 결제** | 결제사 조회 접수. 결제 사실을 부정하지 않고 "우리 쪽 승인 기록이 없다"로 말한다 |
| M-04 | 승인번호 일치 · **금액 불일치** | 부분 취소·분할결제·차액 보상 이력 확인 | 이력으로 설명되면 정상, 안 되면 결제사 조회 접수 |
| M-05 | 승인시각 **±5분 밖** | 같은 고객의 **다른 주문**일 가능성 | 인접 주문을 다시 대조. 확정 전 복구·환불 금지 |
| M-06 | 카드 뒷 4자리 **불일치** | 다른 카드 또는 **타인 결제** | 본인확인 후 진행 (「조합 규정집」 제8조). 명의 확인 전 처리 금지 |
| M-07 | 동일 승인번호 **2건 이상** | 결제사 중복 전송 | 1건 유지·나머지 취소 |
| M-08 | 주문 1건 · **결제 승인 2건** | **중복 결제** | 초과분 환불 |
| M-09 | 네 키 전부 일치 · 주문 레코드가 **일시적으로 조회되지 않음**(반영 지연) | **유실이 아니다** — 시스템 반영 대기 | 반영을 기다린 뒤 **재조회**한다. 즉시 환불·복구하지 않는다 |
| M-10 | 네 키 전부 일치 · 주문이 **다른 계정에 있음** | 계정 귀속 문제 | 계정 명의를 확인하고 **본인 건만** 처리한다 (「조합 규정집」 제8조). 타 계정 주문의 존재·내용을 알려주지 않는다 |

**M-09를 M-01로 오처리하면 정상 주문을 환불한다.** 조회가 "없음"을 반환한 것과 아직 반영되지 않은 것은 다르므로, **승인 직후 건은 M-01로 확정하기 전에 재조회 한 번을 거친다.** 재조회 간격·횟수 상한은 「운영 한도 스펙(파일·조회 상한·폴링·재시도·멱등·동시성·토큰 예산)」 LIM-08이다. **생성 실패 상태의 주문 레코드가 조회되면 그것으로 M-01이 확정된다** — 실패 기록이 있으면 지연(M-09)이 아니다.

M-01 주문 유실을 M-08 중복 결제로 판정하여 환불만 처리하지 않도록 유의한다. 주문이 조회되지 않는다는 사실만으로 중복 결제로 확정하지 않으며, 유실된 주문의 복구 가능 여부를 확인한다. **중복 결제는 결제 승인이 2건일 때만 성립한다.**

## 4. 주문 복구 및 환불 기준

M-01이 확정된 경우 유효한 결제와 고객의 구매 의사에 따라 **주문 복구**를 원칙으로 한다.

| 조건 | 처리 |
|---|---|
| 상품 확보 가능 + 출하 가능 | **주문 복구** — 결제 내역을 원본으로 주문을 재생성하고 정상 출하 |
| 품절·시즌 종료로 출하 불가 | **미배송분 환불** (전액) |
| 지연으로 고객이 더는 원하지 않음 | **미배송분 환불** — 고객 의사를 우선한다 |
| 일부만 출하 가능 | 출하분 유지 + **미배송분만 환불** (부분) |

**환불 기준액도 실결제액**이다(§1과 같은 기준). 복구 시에는 **추가 결제를 요구하지 않는다** — 가격이 그 사이 올랐어도 결제된 금액대로 출하한다.

주문 유실에 대한 처리 책임은 조합에 있다. 기존 결제에 대한 복구 또는 환불 처리를 완료하여야 하며, 고객에게 재주문만 요청하고 종결하지 않는다.

## 5. 대사 키와 판정값

| | 값 |
|---|---|
| 대사 키 | 카드 **뒷 4자리** · 승인번호 · 금액 · 승인 시각 — 전체 번호·유효기간·CVC는 대사 키가 아니다 |
| 뒷 4자리 확인 방식 | **고객이 제시한 값과 대조**한다. 원장 값을 먼저 읽어 주는 필드가 아니다 |
| 조회되지 않은 키 | 확인되지 않음 — 없음과 다른 값이다 |
| 확정 전 상태 | M-05·M-06은 **미확정**이다 |
| 반영 지연 | M-09는 **정상 주문의 지연**이지 유실이 아니다 |
| 증빙 서열 | 고객 제출 캡처는 당사자 제출물이고 승인 기록이 상위다 (「증빙 권위 서열 조항(당사자 제출물 < 제3자 발행물)」 제3조·제9조) |
| 조회 범위 | 결제와 주문을 **둘 다** 조회한다 (§2 ⑴⑵) |

## 6. 고객 안내 문안

**대사 중 (M-01 확정 전)**
> "결제 문자가 정상적으로 발송된 것으로 확인됩니다. 저희 쪽 결제 승인 기록을 먼저 확인하고, 해당 기록과 주문 내역을 대조하겠습니다. 결제하신 카드 뒷 4자리만 확인해 주시면 대조가 정확해집니다."

**M-01 복구**
> "확인 결과, 결제는 정상 승인되었으나 **조합 시스템 오류로 주문서가 생성되지 않았습니다.** 결제 내역 그대로 주문을 복구해 두겠습니다. 다시 결제하실 필요 없습니다."

**M-03**
> "조합의 결제 승인 기록에서 해당 건이 확인되지 않습니다. 결제가 실제로 빠져나갔다면 결제사 쪽 확인이 필요해서 조회를 접수해 두겠습니다 — 결제 사실이 없다는 말씀이 아니고, **저희 기록에서 확인이 안 된다**는 뜻입니다."

(6/6쪽은 M-03 문안 이후 공백)

## 에이전트용 요약 (액션 API 순서)

**공통 순서**
1. 고객에게 **카드 뒷 4자리와 결제 문자의 승인번호·금액·시각**을 먼저 묻는다. 원장 값을 먼저 읽어 주지 않는다. 전체 카드번호·유효기간·CVC는 받지 않는다.
2. **결제 조회**를 한다.
   - 승인번호가 있으면 API_17(approval_no)로 조회한다.
   - 주문번호를 알면 API_18(order_no)로 그 주문의 결제를 본다.
   - 결제의 order_no가 null이면 주문이 연결되지 않은 결제다(M-01 신호).
3. **주문 조회**를 한다. API_07(order_no), 또는 회원 기준 API_08(member_id)로 같은 시각대 주문을 찾는다.
   - 주문 status가 FAILED이고 failure_code가 있으면 생성 실패, 곧 M-01 확정이다.
4. 네 키(승인번호 정확, 금액=실결제액 정확, 시각 ±5분, 뒷 4자리 정확)로 판정한다.
5. 어느 한쪽이라도 조회하지 않았다면 판정하지 않는다. "주문 없음"으로 끝내지 않는다.

**유형별 처리**

| 유형 | 판정 | 액션 순서 |
|---|---|---|
| M-01 주문 유실 (결제 있음, 주문 없음 또는 FAILED) | 승인 직후면 먼저 **한 번 재조회**(M-09 배제). FAILED 기록이 있으면 바로 확정 | 출하 가능하면 **API_22 주문 복구 접수**(path order_no, 본문 없음) → 복구 안내(재결제 불필요, 추가 결제 없음). 품절·시즌 종료·고객 거부면 **API_29 환불**(amount=실결제액 전액, reason에 주문 유실). 일부만 출하 가능하면 API_29로 미배송분만 부분 환불 |
| M-02 주문 취소 상태 | API_07의 refund_ids, API_30(주문별 환불 검색), API_17의 status·cancellation_request_ids 확인 | 환불이 안 됐으면 카드 결제는 **API_31 카드 취소**(approval_no), 또는 API_29. 이미 됐으면 입금 경로와 반영 기간을 안내 |
| M-03 승인 기록 없음 | 결제 미완료 또는 타사 결제 | 결제 사실을 부정하지 않는다("저희 기록에서 확인이 안 된다"). 결제사 조회 API가 없으므로 **API_35**(LANE2_HANDOFF, reason=결제사 조회 요청·승인번호·금액·시각)로 접수 |
| M-04 금액 불일치 | 부분 취소·분할결제·차액 보상 이력 확인(API_17·API_30) | 이력으로 설명되면 정상이라고 설명한다. 아니면 API_35로 결제사 조회 접수 |
| M-05 시각 ±5분 밖 | 다른 주문일 수 있음 | API_08로 인접 주문을 다시 대조한다. 확정 전에는 복구·환불 금지 |
| M-06 뒷 4자리 불일치 | 다른 카드 또는 타인 결제 | 본인 확인 전에는 처리 금지(조합 규정집 제8조). 다른 카드로 결제했는지 다시 묻는다 |
| M-07 동일 승인번호 2건 이상 | 결제사 중복 전송 | 1건만 유지하고 나머지는 **API_31 취소**. 같은 approval_no라 취소 대상이 애매하면 API_35로 이관 |
| M-08 주문 1건에 승인 2건 | **중복 결제**(승인 2건일 때만 성립) | 초과분 결제를 **API_31 카드 취소**(초과분 approval_no) 또는 API_29로 초과분 환불 |
| M-09 반영 지연 | 유실이 아님 | 기다린 뒤 재조회한다. 즉시 환불·복구하지 않는다. 고객에게는 반영 대기 중이라고 안내한다 |
| M-10 다른 계정에 있는 주문 | 계정 귀속 문제 | 명의를 확인하고 본인 건만 처리한다. **다른 계정 주문이 있는지조차 알려 주지 않는다** |

**주의**
- 주문이 안 보인다는 이유만으로 중복 결제(M-08)로 판정해 환불만 하지 않는다. M-01이면 복구가 원칙이다.
- 주문 유실은 조합 책임이다. 재주문만 요청하고 끝내지 않는다. 복구할 때 가격이 올랐어도 추가 결제를 받지 않는다.
- 금액은 항상 **실결제액**(카드·포인트·쿠폰 합) 기준이다. 분할결제를 카드분만 따로 대사하지 않는다.
- 고객 캡처보다 승인 기록이 우선한다(조합 규정집 제26조).
- 안내할 때는 유형, 처리 내용, 반영 기간을 함께 말한다. 문안은 §6을 따른다.
